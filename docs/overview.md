# Section 4: PyTorch-Chipyard

PyTorch-Chipyard is a framework that compiles Torch models for Chipyard backend
targets and enables model-level execution. Internally, it lowers `torch.ops`
through the Triton-Chipyard backend. It is connected behind PyTorch Inductor, so
the generated model runner can preserve Inductor optimizations such as fusion
rules.

## 4.1 PyTorch-Chipyard

![PyTorch-Chipyard system overview](figures/system-overview.png)

PyTorch-Chipyard primarily uses ahead-of-time compilation. This design is used
because the Chipyard runtime does not support the Python environment required to
implement PyTorch 2.0 JIT compilation directly. Instead, PyTorch-Chipyard adds a
C++ model-runner wrapping layer after Inductor, where the FX graph containing
the actual Torch model execution information has already been lowered. It also
connects Triton-Chipyard, which lowers the Triton kernels generated by Inductor
to RISC-V, making FPGA simulation possible.

For execution on Chipyard, PyTorch-Chipyard provides not only the model runner
but also runtime-ready packed artifacts such as the Torch model's weight
parameters and inputs. The model runner produces outputs that can be used to
check whether the kernels executed correctly, and users can bring the model
result back into PyTorch for validation. The model runner also emits
`model.log`, which records full-model execution results and per-kernel cycle
counts, and `autotune.log`, which summarizes autotuning results for the
multiple autotuning kernels generated by TorchInductor. These logs help users
understand the execution results in more detail.

## 4.2 Triton-Chipyard

![Triton-Chipyard compilation flow](figures/compilation-flow.png)

The figure above shows the Triton-Chipyard lowering path. Triton-Chipyard is
based on Triton-Shared and is organized as a compilation pipeline across
Triton, Triton-Chipyard, Buddy-MLIR, and LLVM.

The representative work done at each stage is:

- `triton-chipyard-opt`

  This stage lowers `tt.load` operations generated from the `tl.load` Triton
  Python API and performs buffer materialization. The default
  `triton-shared-opt` assumes a general execution environment and lowers through
  an `alloc + copy` pattern. In contrast, `triton-chipyard-opt` is adapted to
  the Chipyard system model where multiple hardware blocks share one RAM. It
  first aliases shared buffers and only performs `alloc + copy` for the aliased
  portions that need it, such as masked accesses or module-pointer uses. To
  preserve execution stability, Triton-Chipyard does not expose primitives for
  directly programming memory that belongs to a single hardware unit, such as a
  Gemmini scratchpad.

- `buddy-opt`

  This stage lowers the `linalg.matmul` operations generated by
  `triton-chipyard-opt` from `tt.dot` or `tl.dot` to the selected Chipyard
  hardware path. It supports pure CPU matmul, Gemmini matmul, and vector matmul
  through Saturn, but currently only one hardware target can be used at a time.

- `buddy-translate` and `buddy-llc`

  These stages run after `buddy-opt` and lower the program to actual binary
  code, including register selection.
